## 1. 상호명 추출 → 검증 파이프라인

### 문제: "블로그 개수에 비해 근거가 적다"

처음엔 LLM(Gemini)이 상호명을 너무 엄격하게 걸러낸다고 의심했다. 실측해보니:

| 키워드 | 블로그 수 | 상호명 추출됨 | distinct 상호 | top10에 남는 언급수 |
|---|---|---|---|---|
| 이태원 브런치 | 35 | 35 (100%) | 17 | 28 |
| 강남 맛집 | 35 | 33 (94%) | 31 | **13** |

LLM 필터링 손실은 0~9%뿐이었다. **진짜 원인은 `top_n`이 distinct 상호 개수를 자르는
것**이었다 — "강남 맛집"처럼 업종이 다양한 키워드는 상호가 31개나 나오는데 상위 10개만
보여주니 22개 업체가 통째로 사라졌다. 이건 사용자가 "트렌드 랭킹을 보려고 일부러 넣은
기능"이라 확인했고, **그대로 유지**하기로 했다 (`service.py`의 `top_n` 슬라이싱).

### 문제: 카카오 매칭이 "아무 곳이나" 반환하던 것

`kakao.py`의 `_pick_best_match`는 원래 이름이 하나도 안 맞아도 **가장 가까운 곳을
무조건 반환**했다. 상호명이 다르면(예: 오타, LLM이 잘못 뽑은 이름) 엉뚱한 가게에
블로그 언급이 잘못 붙는 문제가 있었다.

**해결**: `require_match=True`를 추가해서, 이름이 안 맞으면 `None`을 반환하도록 함.
대신 이제 진짜 필터링이 필요해졌으므로 LLM 추출 규칙을 반대로 **느슨하게** 풀었다
("확신 없어도 최대한 추출하고, 실존 여부는 카카오맵이 검증하게 하라") — 정밀도 검증
책임을 LLM 판단에서 카카오맵 실존 확인으로 옮긴 것.

### 문제: 표기 차이로 진짜 업체를 놓침

`require_match=True`를 단순 부분일치로만 구현하니, 표기가 살짝 다른 진짜 업체를
놓쳤다:

- `메가커피 신논현역점` (블로그) vs `메가MGC커피 신논현역점` (카카오 등록명) — "MGC" 누락
- `투썸플레이스 2.0 강남` vs `투썸플레이스 투썸2.0강남` — 어순/중복 다름
- `브리피트` vs `브리비트 성수` — 오타 1글자

**해결 1 — 퍼지 매칭**: `difflib.SequenceMatcher`로 유사도 계산, 임계값 0.75
(`FUZZY_MATCH_THRESHOLD`). 실측으로 임계값을 정했다 — 진짜 근접매치는 0.86~0.96,
완전 다른 지점은 0.46, 무관한 결과는 0.00으로 깔끔하게 갈렸다.

**해결 2 — 네이버 지역검색 폴백**: 카카오 직접 매칭이 실패하면, 네이버 공식 지역검색
API(`openapi.naver.com/v1/search/local.json`, `naver_local_search()`)로 그 이름을
재조회해서 네이버 등록명을 얻고, 그 이름으로 카카오를 재검색한다. 네이버 블로그
글쓴이는 보통 네이버 지도 기준으로 상호명을 태그하기 때문에, 카카오보다 네이버 쪽
등록명이 블로그 원문과 더 잘 맞는 경우가 많다.

```
1. 카카오에 원래 이름 그대로 검색 (퍼지 매칭 포함)
2. 실패 → 네이버 지역검색으로 등록명 재확인 → 그 이름으로 카카오 재검색
3. (지역 관련 폴백은 2장 참고)
```

**시도했지만 안 쓴 것**: 비공식 `map.naver.com` 내부 검색 API — 캡차(ncaptcha)로
막혀 있어서 프로그램적으로 우회하지 않기로 함 (정책상, 안정성상 둘 다 이유).

### 문제: 검색 키워드와 무관한 결과가 섞임

"강남 영화관"을 검색했는데 "강남 실내놀거리 15선" 같은 listicle 글에서 팝업스토어
("일상비일상의틈")까지 뽑혀 나왔다. 원인: LLM 프롬프트가 검색 키워드를 아예 몰랐다
— 그냥 "글에 나온 업체 다 뽑아"만 하고 있었다.

**해결**: 프롬프트에 검색 키워드를 명시하고 "키워드 주제와 무관한 업종·시설은
제외" 규칙 추가 (`gemini.py`의 `PROMPT_TEMPLATE`). 검증: "강남 영화관" 추출 후보
35개(잡다한 것 포함) → 9개(전부 진짜 영화관)로 정리됨.

## 2. 지역/반경(radius) 처리

가장 많이 갈아엎은 부분. 원래 코드는 `area_keyword = keyword.split()[0]` — 검색어
첫 단어를 무조건 지역명으로 취급했다.

### 왜 반경 필터가 존재하는가 (삭제하지 않은 이유)

"근거량이 준다"는 의심에 반경을 없앨지 검토했지만, 실측 결과 **기본값(5km)에서는
근거량에 거의 영향이 없었다** — 5km→20km로 넓혀도 검증 성공률이 31→32로 거의 그대로
였고, 유일하게 늘어난 1건("CGV 판교")은 사실 강남이 아니라 성남시 분당구였다. 즉
반경 필터는 **동명이인 업체(다른 도시의 같은 이름 가게)를 걸러내는 정당한 기능**이라
판단, 유지하기로 했다.

### 문제 1: 지역명이 없으면 엉뚱한 기준점이 잡힘

"영화관 큰 곳"처럼 지역명이 없는 검색은 `area_keyword`가 "영화관" 자체가 되고,
카카오에 "영화관"을 검색해서 1등으로 나온 **특정 지점(CGV 용산아이파크몰)의 좌표**가
기준점이 됐다. 전국을 찾고 싶었는데 결과가 용산 반경 5km로 왜곡됨.

### 문제 2: 여러 지역을 동시에 검색할 수 없음, 그리고 순서에 따라 결과가 달라짐

`keyword.split()[0]`은 **첫 단어만** 지역으로 쓴다. "성남 서울 영화관"과 "서울 성남
영화관"은 사용자 입장에서 같은 의도인데, 전자는 "성남"만, 후자는 "서울"만 기준점이
되어 **완전히 다른 결과**가 나왔다 (실측: "성남 서울" → 후보 4개 전부 성남,
서울은 0개).

이때 중요한 구분을 했다 — **블로그 검색(Naver) 자체는 정상**이었다. "성남 서울
영화관"으로 블로그를 모으면 두 지역 콘텐츠가 자연스럽게 섞여서 잘 나온다 (사용자
표현: "AND 연산이라 자연스러운 것"). 문제는 그 다음 우리 자체 코드(카카오 반경
검증)가 첫 단어 하나만 보고 나머지 지역을 통째로 버리는 것이었다 — 이건 "우리
시스템 탓"이 맞다는 데 합의.

### 시도 1 (실패): Gemini 한 번 호출에 지역+상호명 같이 받기

지역 추출을 상호명 추출과 같은 프롬프트/스키마에 욱여넣었더니, LLM이 "검색어에서만"
지역을 뽑으라는 지시를 무시하고 **블로그 본문 전체에서 언급된 온갖 지역**(부산, 광주,
청주...)까지 다 끌어모았다. 지시가 방대한 블로그 본문 컨텍스트에 묻힌 것으로 추정.

### 시도 2 (채택): 지역 추출을 완전히 분리된 작은 호출로

`extract_regions(keyword)`를 신설 — 블로그 본문은 아예 안 보여주고 검색어
문자열 하나만 Gemini에 넘긴다. 결과가 안정적으로 정확해짐:

```
"성남 서울 영화관" -> ['성남', '서울']
"서울 성남 영화관" -> ['서울', '성남']   # 순서 달라도 둘 다 인식
"영화관 큰 곳"      -> []               # 지역 없음, 정확히 빈 배열
"신논현역 카공"      -> ['신논현역']       # 역 이름도 인식 (주소 검색 API는 이걸 못 잡음)
"송리단길 카공"      -> ['송리단길']       # 골목상권 이름도 인식
```

`신논현역`, `송리단길` 같은 콜로키얼한 지명은 카카오 "주소 검색" API로는 아예 안
잡힌다는 것도 미리 확인했다 (0건 반환) — 그래서 정규식/주소API 기반이 아니라 LLM
기반으로 갔다.

### 최종 검증 순서 (`service.py`의 `_resolve_place`)

```
1. Gemini가 뽑은 지역 각각에 대해 카카오 검증 시도 (순서 무관, 하나라도 맞으면 확정)
2. 다 실패하면 네이버 지역검색으로 이름 재확인 → 각 지역에 재시도
3. 그래도 실패하면 지역 제한 없이 전국 검색
   (regions가 애초에 빈 배열이었던 경우도 곧장 여기로 옴)
```

### 문제 3: 전국 폴백이 무관한 도시까지 허용

3단계 전국 폴백을 넣고 나니 새 문제가 생겼다 — "성남 서울" 검색에 **수원**에 있는
"CGV 광교"가 섞여 나왔다. 원인: "CGV 광교"가 성남/서울 반경 검증엔 실패하고, 전국
폴백에서는 **지역 제한이 아예 없어서** 무조건 통과됐다.

**해결**: 전국 폴백 결과의 주소(`road_address_name`/`address_name`)에 검색된
지역명이 실제로 텍스트로 포함되는지 확인하는 `_address_matches_regions()` 필터
추가. `regions`가 비어 있으면(진짜 지역 없는 검색) 필터 없이 통과, `regions`가
있으면 그 지역명이 주소에 있어야만 통과.

```python
# 검증
search_place('CGV 광교', nationwide=True, regions=['성남','서울'])  # None (수원 → 거부)
search_place('CGV 천호', nationwide=True, regions=['성남','서울'])  # 통과 ('서울' 포함)
search_place('CGV 광교', nationwide=True, regions=[])              # 통과 (지역 제한 없음)
```

## 3. 동점(mention_count 동률) 처리

언급 횟수가 같은 후보가 여러 개일 때 어떤 순서로 보여줄지가 모호했다. 원래는
Python `sort()`가 stable sort라서 **먼저 카카오 검증에 성공한 순서**(≈ Gemini가
결과를 반환한 순서, 사실상 우연)가 유지되고 있었다 — 사용자가 이해할 수 있는
기준이 아니었다.

세 가지 옵션을 검토:
1. 검색 지역 기준점에서 가까운 순 **← 채택**
2. 가나다순 (단순하지만 무의미)
3. 순서는 그대로 두고 UI에서 동점임을 표시

**구현**: `_sort_candidates()`에서 `(-mention_count, distance_to_anchor)` 튜플로
정렬. 기준점은 감지된 지역 중 첫 번째(`regions[0]`)의 좌표. 지역 정보가 아예 없으면
(예: "영화관 큰 곳") 기존처럼 검증 순서를 유지.

구현 중 `get_area_anchor()`가 카카오 API 원본 응답을 그대로 반환해서 좌표가
**문자열**이었던 기존 버그를 발견 (`float()` 변환 누락) — 지금까지는 요청
파라미터로만 쓰여서 안 드러났는데, 거리 계산에 쓰면서 `TypeError`로 표면화됨. 같이
고침.

## 4. 프론트엔드 버그들

| 증상 | 원인 | 해결 |
|---|---|---|
| 블로그 제목이 `&lt;알베르&gt;`처럼 깨짐 | 네이버 API 응답의 HTML 엔티티를 `<strong>` 태그만 제거하고 안 풀어줌 | `html.unescape()` 추가 |
| 모바일에서 "근거 보기" 펼치면 카드 밖으로 넘침 | `.sources a`가 `display:flex`라서 내부 텍스트가 축소 불가능한 익명 flex 아이템이 됨 → `overflow:hidden`/`ellipsis`가 무력화 | 제목을 별도 `<span class="source-title">`으로 감싸고 `min-width:0`, `overflow-wrap:anywhere`로 줄바꿈되게 함 |
| 검색창 탭하면 iOS에서 화면이 확대됨 | `<input>` font-size가 15px (iOS는 16px 미만이면 자동 확대) | 16px로 변경 |
| 브라우저 탭 제목이 안 바뀜 | `<svelte:head><title>`을 고쳤는데 실제로는 안 먹힘 — 일반 Vite SPA라 `svelte:head`는 JS 로드 *후* 런타임에만 반영되고, 원본 HTML(`frontend/index.html`)의 정적 `<title>`이 진짜 탭 제목을 결정함 | `frontend/index.html`의 정적 title도 같이 수정 |

## 5. CI/CD 파이프라인

`.github/workflows/ci-cd.yml`: push/PR마다 백엔드 테스트·프론트엔드 빌드·Docker
빌드를 검증하고, `main` 직접 push + 검증 통과 시에만 배포.

- **배포 대상이 Windows + WSL 서버**라 `wsl.exe -- bash -s`로 WSL 진입 후 커맨드
  실행 (순정 OpenSSH 서버, `appleboy/ssh-action` 같은 서드파티 액션 대신 직접
  `ssh` 사용).
- 초기엔 `backend-test`와 `frontend-build`가 병렬로 돌면서 `frontend/dist`가
  없는 상태로 테스트가 돌아 `test_frontend_is_served_from_backend`가 실패 —
  `frontend-build`가 dist를 아티팩트로 올리고 `backend-test`가 그걸 받아쓰도록
  `needs`로 순서를 강제함.
- `DEPLOY_PATH`를 처음엔 GitHub Secret으로 뒀다가, 실제로는 워크스페이스 루트
  (`joonspace/`)와 레포가 clone된 하위 폴더(`joonspace/naver-blog-to-kakao-map`)가
  달라서 `fatal: not a git repository` 에러 발생 — 정확한 경로로 하드코딩.
  (Secret으로 관리하지 않은 이유: 경로 자체는 민감 정보가 아니고, 워크플로우
  파일에서 바로 보이는 게 디버깅에 유리해서.)
- 초기 배포 실패 원인이 "SSH_HOST 연결 불가"였는데, 에러 메시지가 애매해서
  ssh-keyscan을 명시적 타임아웃+에러 메시지가 나오도록 스텝을 보강함
  (`::error::${SSH_HOST}:${SSH_PORT}에 연결할 수 없습니다...`).

필요한 GitHub Secrets: `SSH_PRIVATE_KEY`, `SSH_HOST`(또는 `SERVER_HOST`),
`SSH_PORT`, `SSH_USER`(또는 `SERVER_USER`). 자세한 건 README의 CI/CD 섹션 참고.

## 6. Gemini 응답 재현성 (temperature)

똑같은 키워드로 반복 검색했는데 결과가 매번 달랐다 ("신논현역 카공"을 5번 검색하면
5번 다 다른 언급 횟수가 나옴). 원인 조사:

- `gemini.py`의 API 호출에 `temperature`를 아예 설정 안 해서 기본 샘플링 랜덤성을
  쓰고 있었다.
- 70개 블로그 글처럼 큰 배치를 한 프롬프트에 넣으면, 이 랜덤성이 "같은 업체를 1회
  언급으로 볼지 41회로 볼지"까지 좌우할 정도로 결과를 크게 흔들었다 (실측 확인:
  같은 입력에 대해 셀렉토커피 관련 언급이 1회~41회까지 요동침, 실제로는 41회가
  맞는 값이었음 — 본문에 "셀렉토" 언급된 글이 실제로 41개 있었다).
- 배치를 잘게 나눠서 처리하는 것도 시도해봤지만, 배치 크기에 따라 정확도가
  비단조적으로 오르내려서(7→13개, 10→7개, 15→15개, 20→4개, 실제는 41개) 규칙을
  못 찾음. 복잡도만 늘고 확실한 이득이 없어 도입 안 함.
- `temperature=0`을 추가하니 배치 크기와 무관하게 **같은 입력에 항상 같은 결과**가
  나왔다 (5번 반복 검증). 반복검색 시 결과가 달라지는 핵심 문제는 이걸로 해결됨.
  단, 정확도(진짜 값에 얼마나 가까운지) 자체를 보장하진 않는다 — 그건 별개 문제.

## 7. 여행지 개요(Overview) 화면

"부산여행"처럼 넓은 여행 키워드는 지역이 하나로 특정이 안 돼서(2장 참고) 바로
상호명을 뽑기보다, 먼저 "이 여행지엔 이런 동네·카테고리가 있어요"를 보여주고
사용자가 관심 있는 지역+카테고리를 고르게 하는 게 낫다고 판단했다.

- `extract_region_overview()` (`gemini.py`): 블로그 글에서 지역→카테고리 구조와
  언급 빈도만 추출하고, 상호명은 이 단계에서 뽑지 않는다. 기존 `extract_business_names`와
  같은 `_call_gemini()`를 재사용(temperature=0 그대로 적용됨).
- 지역+카테고리를 클릭하면 **새 매칭 로직을 만들지 않고**, `"{지역} {카테고리}"`
  형태의 키워드로 기존 `preview_collection`(카카오 검증까지 포함)을 그대로 재사용한다.
  개요 단계는 정확한 숫자를 보장하지 않는 "대략의 지도" 역할이고, 실제 검증은
  드릴다운했을 때 기존 파이프라인이 담당하는 구조.
- 프론트엔드는 기존 검색과 완전히 분리된 탭("빠른 검색" / "여행지 개요")으로 진입한다
  — 키워드를 보고 자동으로 모드를 판단하지 않기로 함(오판 리스크, 사용자 승인 하에 결정).

**알려진 한계**: 개요 단계도 큰 배치(수십~백여 개 글)를 한 번에 처리하므로, 6장에서
설명한 것과 같은 종류의 부정확성(temperature=0으로 일관되긴 하지만 진짜 값과 다를 수
있음)이 있을 수 있다. 정확한 숫자는 드릴다운 단계에서 확정되므로 지금은 수용.

## 8. 알려진 한계 / 다음에 볼 것

- **동일 지역명, 다른 실제 위치**: 지역명이 여러 동네에 걸쳐 있으면(예: 매우 넓은
  "서울"), 단일 anchor+radius로는 그 지역 전체를 대표하기 어렵다. 지금은 전국
  폴백 + 주소 텍스트 필터로 어느 정도 완화했지만, 완벽하진 않다.
- **전국 폴백의 카카오 API 호출 비용**: 지역 매칭이 실패하는 후보가 많을수록
  네이버 재조회 + 전국 재검색까지 가는 케이스가 늘어나 API 호출이 늘어난다.
  Kakao REST 무료 쿼터 안에서는 문제없는 수준이지만, 검색량이 크게 늘면 재검토
  필요.
- **동점 처리의 지역 기준점**: 지역이 여러 개 감지되면 `regions[0]`(리스트의 첫
  지역)만 기준점으로 쓴다 — 예를 들어 "성남 서울" 검색에서 서울 후보들끼리의
  동점은 "성남" 기준으로 거리를 재게 된다. 지금은 그렇게 두기로 했지만, 더
  정교하게 하려면 "가장 가까운 감지 지역과의 거리"로 바꿀 수 있다.
- **`top_business_names`(gemini.py)**: 현재 어디서도 호출하지 않는 죽은 코드.
  기존부터 있던 것이라 그대로 뒀음.

## 9. 배치 추출 논쟁의 진짜 원인은 프롬프트였다

"강남 맛집"을 검색하면 블로그 100개를 모아도 카드 하나당 근거가 2~3개뿐이었다.
더 파보려고 30페이지(글 210개)까지 밀어붙였더니, 2회 이상 언급된 후보가 오히려
9~10개 → **2개**로 줄었다. 처음엔 이걸 "lost in the middle"(긴 문맥 중간 정보 누락)로
진단하고 글을 작은 배치로 나눠 여러 번 호출하는 계획을 세웠다(`BATCH_SIZE=15`).

### 실측: 배치를 잘게 쪼개도 문제가 그대로였다

"신논현 카공"(제목에 "셀렉토"가 명시된, 즉 확실히 리뷰 대상인 글이 40개 있는
ground truth 셋)으로 배치 크기별 recall을 실측:

| 배치 크기 | 호출 수 | 추출된 진짜 언급 수 (실제 40개) |
| --- | --- | --- |
| 15 (최초 계획) | 5 | 5 |
| 8 | 9 | 9 |
| 5 | 14 | 14 |
| 3 | 24 | 24 |
| 2 | 35 | 30 |
| 1 (글 하나당 호출 하나) | 70 | **40** |

배치를 2로만 줄여도 recall이 뚝 떨어졌다 — 글 2개를 같이 보여줬을 뿐인데 74%
recall로 무너진다는 건, 단순히 "컨텍스트가 길어서" 생기는 현상(고전적
lost-in-the-middle)이라 보기엔 규모가 너무 작았다. 뭔가 다른 원인이 있다고 보고
프롬프트를 다시 읽었다.

### 진짜 원인: "통일해서 출력하세요" 규칙의 모호함

`PROMPT_TEMPLATE`에 있던 규칙:

> 같은 가게가 여러 항목에서 다른 표기로 언급되더라도 동일한 상호명 하나로
> 통일해서 출력하세요.

의도는 "표기만 통일해라"(예: "메가커피"/"메가MGC커피" → 같은 이름으로)였는데,
응답 스키마가 `index`+`name` 쌍의 배열이다 보니 모델이 이 규칙을 "같은 가게는
결과에 한 번만 내보내라"로 해석해서 나머지 항목(index)을 통째로 누락시키고
있었다. 배치가 클수록 같은 가게가 반복 등장할 확률이 높아지니, 배치 크기가 클수록
이 스킵 현상이 더 심해져서 "lost in the middle"처럼 보였던 것뿐이었다.

규칙을 아래처럼 "개수는 유지, 표기만 통일"이라고 명시적으로 갈라서 다시 쓰니:

> 같은 가게가 여러 항목에서 언급되면, 항목마다 각각 결과에 포함하세요(항목을
> 건너뛰지 마세요). 다만 표기가 항목마다 다르더라도... name 값은 동일한 상호명
> 하나로 통일해서 쓰세요.

**배치 없이 70개 글을 한 번에 넣어도 40/40 recall**이 나왔다. "강남 맛집"
210개 글 기준으로도 배치 없이 한 번에 처리한 쪽(확신 후보 44개)이 배치=15로
나눈 쪽(29개)보다 오히려 나았다 — 배치로 쪼개면 모델이 전체 글 사이의 반복
언급을 한눈에 못 보게 되는 손해가 더 컸던 것으로 보인다.

**결론: 배치 분할은 도입하지 않았다.** 프롬프트의 모호한 규칙 하나가 원인의
전부였고, `gemini.py`는 posts 전체를 한 번에 호출한다. (6장에서 이미 "배치
크기별로 비단조적으로 오르내려서 규칙을 못 찾았다"고 적어둔 것도, 사실은 같은
프롬프트 버그가 배치 크기마다 다른 정도로 나타난 결과였을 가능성이 높다.)

### 후속: 워딩만으로는 불안하다는 지적 → 구조적으로 강제

프롬프트 워딩 수정은 실측으로 검증됐지만, 자연어 규칙이라 모델 버전이 바뀌거나
표현이 조금만 달라져도 다시 깨질 수 있다는 지적이 있었다(정당한 지적). 그래서
"워딩을 더 잘 쓰는" 대신 "몇 개를 스킵하면 아예 스키마 위반이 되게" 만들었다:

- `_business_names_schema(post_count)`: 응답 배열에 `minItems`/`maxItems`를
  `post_count`로 고정. 상호명이 없는 항목은 `name: ""`로 채우도록 프롬프트에도
  명시. 이러면 "몇 개를 냈는지"는 프롬프트 해석이 아니라 API가 강제하는 값이 된다.
- 실측: `minItems=maxItems=135`까지는 정상 동작(200), **140부터 API가 400
  Bad Request로 요청 자체를 거부**했다(정확도와 무관한 별개의 제약). 여유를 두고
  `MAX_ITEMS_PER_CALL = 100`으로 다시 나눠 호출하도록 되돌렸다 — 단, 이번엔
  "정확도 때문"이 아니라 순수히 "API가 이 크기 이상의 고정 길이 스키마를
  거부해서"이고, 나눈 청크마다 그 청크 크기만큼 길이가 고정된 스키마를 쓴다.
- 재검증("강남 맛집", 글 210개): 400 에러 없이 확신 후보 34~35개로 안정적으로
  나옴 (배치 없이 한 번에 처리했던 44개보다는 약간 낮지만, 최초 버그였던 2개와는
  비교가 안 되게 개선됐고, 청크 경계 때문에 생기는 근소한 차이로 판단해 수용).

## 10. 결과 개수를 확신 후보 수에 맞춰 늘리기

추출 정확도 문제(9장)를 고치고 나니, "좁은 지역은 적게, 넓은 지역은 검색도 많이
하고 결과도 많이 보여줘야 한다"는 원래 요청을 제대로 구현할 수 있게 됐다.

- `_finalize_candidates`: 2회 이상 언급된 "확신 후보"를 최대 30개(`MAX_TOP_N`)까지
  전부 보여준다. 확신 후보가 5개(`MIN_REPEATED_CANDIDATES`)에 못 미치면(좁은
  검색) 결과가 텅 비어 보이지 않도록 1회 언급 후보까지 포함해 상위 5개를 채운다.
- `_collect_candidates`의 tier 반복 중단 조건: 확신 후보 수가 직전 tier보다
  최소 기준(5개)을 넘긴 뒤에도 **여전히 늘고 있으면** 계속 다음 tier로 진행한다.
  늘지 않거나(정체) 줄어들면 멈춘다.
- 실측(강남 맛집): tier마다 확신 후보 11 → 19 → 29(성수동 브런치 기준) / tier마다
  꾸준히 느는 케이스는 PAGE_TIERS 끝까지(30페이지) 간다 — 이건 "성수동 브런치"처럼
  실제로 결과가 많은 지역명에서는 원래 예상(5페이지에서 빨리 끝남)과 다르게 끝까지
  가지만, "느는 동안 계속 모은다"는 원칙 자체가 그렇게 설계된 것이라 의도된
  동작으로 판단했다.

## 11. "부산여행"이 다시 결과 목록으로 나온 문제 — 개수만으로는 부족했다

9~10장 작업(추출 정확도 개선 + 결과 개수 확대) 이후 "부산여행"을 다시 검색해보니
`mode: "results"`(평평한 목록)로 나왔다. 애초에 "여행지 개요" 기능은 정확히 이
키워드를 위해 만든 건데(7장), 확신 후보가 20개나 나와서 `_enough_repeat_candidates`
(확신 후보 5개 이상) 기준을 가볍게 통과해버린 것이다.

목록 내용을 보면 문제가 뚜렷했다: 파라다이스호텔부산(해운대 호텔), 해동용궁사(기장
사찰), 톤쇼우 광안점(광안리 식당), 부평깡통시장(남포동 시장), 롯데백화점 부산본점
(서면 백화점)처럼 **완전히 다른 동네·완전히 다른 업종이 한 목록에 뒤섞였다**.
"강남 맛집"처럼 한 동네·한 업종으로 묶이는 넓은 검색과 근본적으로 다른 케이스인데,
지금 판단 기준은 "후보가 몇 개 있냐"만 볼 뿐 "이 후보들이 한 지역으로 묶이냐"는
전혀 보지 않았다.

### 첫 시도: 확신 후보끼리의 최대 거리 — 실패

확신 후보들의 좌표 중 가장 먼 두 지점 사이 거리로 판단해봤다. 실측(`_collect_candidates`
결과의 좌표 직접 계산):

| 키워드 | 확신 후보 최대 거리 |
| --- | --- |
| 성수동 브런치 | 5.1km |
| 강남 맛집 | 6.3km |
| 부산여행 | 22.9km |

10km를 기준으로 삼아 구현했는데, 재검증 과정에서 "강남 맛집"도 `overview`로
잘못 빠지는 게 발견됐다. 원인은 카카오 매칭이 가끔 잘못 걸리는 후보 하나(예:
"강남 맛집" 검색인데 실제로는 200km 떨어진 동명 업체가 매칭됨, 또는 성수동의
느슨하게 매칭된 후보)가 **최대값 하나만으로 전체를 오판**시킨 것 — outlier
하나에 극도로 취약한 지표였다.

### 두 번째 시도: 지역 기준점(anchor) 근처 비율 — 채택

`_sort_candidates`에서 이미 쓰던 `get_area_anchor(regions[0])`(검색어에서 감지된
첫 지역의 좌표)를 기준점으로 삼아, "확신 후보 중 몇 %가 기준점 5km 이내에 있는지"로
바꿨다. 최대값이 아니라 비율이라, outlier 한둘에 흔들리지 않는다. 실측:

| 키워드 | anchor 5km 이내 비율 |
| --- | --- |
| 강남 맛집 | 97% (38개 중 37개, outlier 1개 제외) |
| 성수동 브런치 | (강남 맛집과 유사하게 높은 비율로 클러스터) |
| 부산여행 | 63% (19개 중 12개, 나머지는 7~15km 밖 다른 동네) |

70%를 기준(`SCATTER_MIN_CLUSTER_FRACTION`)으로 삼으니 세 키워드 모두 의도한 대로
갈렸다 — `_is_scattered()`(`service.py`), 결과/개요 판단(`search_collection`)에서
`_enough_repeat_candidates`와 함께 사용. `_collect_candidates`가 이제 감지된
`regions`도 함께 반환해서 재계산 없이 재사용한다.

**교훈**: "이 목록이 하나로 묶이는가"를 판단할 땐 최대/최소 같은 극값보다 "기준점
근처에 얼마나 모여 있는가" 같은 비율 지표가 outlier에 훨씬 강하다.

## 12. 진행 메시지가 거짓말을 하고 있었다 + 실제 병목(카카오 검증) 최적화

사용자가 "최종 결과를 정리하고 있어요" 메시지가 가장 오래 떠 있다고 알려줬다.
확인해보니 두 가지가 겹친 문제였다.

### 진행 메시지는 실제 진행 상황과 무관한 가짜 타이머였다

`App.svelte`의 진행 메시지는 백엔드 상태를 전혀 모른 채, 4.5초마다 다음 메시지로
넘어가다 마지막에서 멈추는 `setInterval` 하나였다. 메시지가 4개뿐이라 검색
시작 13.5초 후부터는 실제로 뭘 하고 있든 무조건 마지막 메시지("최종 결과를
정리하고 있어요")에 고정된다. 검색이 보통 40초~150초+ 걸리니, 사용자 눈엔
"정리하는 중"이 90% 이상의 시간 동안 떠 있는 것처럼 보였다 — 그 단계가 실제로
느려서가 아니라, 표시할 메시지가 먼저 바닥났을 뿐이었다.

### 실측: 진짜 병목은 "정리"가 아니라 카카오 검증이었다

각 단계를 직접 타이밍 측정(30페이지, 강남 맛집):

| 단계 | 시간 | 비중 |
| --- | --- | --- |
| 블로그 수집 | 12.6s | 22% |
| 상호명 추출(Gemini) | 12.9s | 23% |
| **카카오 검증** | **29.8s** | **53%** |
| 최종화(영업시간 등) | 0.1s | 0% |

카카오 검증(`_verified_candidates`)이 절반을 넘게 차지했다. 원인 두 가지:
1. **중복 이름을 그대로 다시 검증**: 같은 업체가 여러 글에서 추출되면(예: 5번
   언급) `_resolve_place`를 5번 다 호출하고 있었다 — 실제로는 이름이 같으면
   결과도 같으니 1번만 하면 됐다.
2. **순차 호출**: 이름마다 카카오 검색 → (실패 시) 네이버 재조회 → 전국
   재검색까지 순서대로 기다렸다. 전부 네트워크 I/O 대기라 병렬로 돌려도 무방했다.

`_verified_candidates`를 고쳐서: 이름 기준으로 먼저 묶어(언급 횟수는 그대로
누적) **고유한 이름만** `ThreadPoolExecutor`(worker 8개)로 동시에 검증하도록
바꿨다. 카카오 클라이언트에 모듈 전역 캐시(`_area_anchors`)가 있어 동시 접근을
확인했는데, 단순 dict 쓰기라 최악의 경우 캐시 워밍업 때 중복 호출 몇 번 더
나가는 정도라 문제없다고 판단(락 안 걸었다).

**효과** (같은 30페이지 강남 맛집 재측정): 카카오 검증 29.8s → **3.2s**(약 9배),
전체 56.5s → 23.9s. 실제 전체 파이프라인("성수동 브런치")도 재검색해보니
75~100초대에서 **약 50초**로 줄었다. 결과 개수·언급 횟수·근거는 이전과 동일함을
확인(회귀 없음).

### 진행 메시지도 정직하게 수정

병목이 줄었어도 넓은 검색은 여전히 오래 걸리므로, 마지막 메시지를 "최종 결과를
정리하고 있어요"(거의 다 됐다는 인상)에서 "카카오맵에서 실제 있는 곳인지 하나씩
확인하고 있어요"(실제로 가장 오래 걸리는 단계를 있는 그대로 설명)로 바꿨다.
완벽한 해결책(백엔드가 실시간 진행률을 알려주는 것)은 아니지만, 최소 변경으로
거짓 인상은 없앴다.

## 13. 블로그 수집을 비공식 스크래핑에서 공식 API로 전환

"강남 카공" 결과를 디버깅하다 보니, 결과 품질(어떤 후보가 몰리는지, 몇 개나
잡히는지)이 결국 원본 블로그 검색 결과 자체에 크게 좌우된다는 게 반복 확인됐다.
`naver_blog_search`는 계속 `section.blog.naver.com/ajax/SearchList.naver`라는
**비공식 엔드포인트**(네이버 블로그 내 검색 위젯을 그대로 흉내낸 것, 문서화 안
됨, JSON 하이재킹 방지 접두사를 직접 벗겨내야 했음)를 쓰고 있었다. 공식
API(`openapi.naver.com/v1/search/blog.json`)로 바꾸기로 했다.

### 전환 전 확인한 것

- `naver_local_search`가 이미 같은 공식 API 계열을 쓰고 있어서 자격증명
  (`NAVER_CLIENT_ID`/`SECRET`)은 이미 준비돼 있었다.
- 콘텐츠 품질 손실 우려를 실측으로 확인: "성수동 브런치" 기준 공식 API의
  `description`(~106~115자)과 비공식 `contents`(~126~162자)가 큰 차이 없었다.
- 공식 API는 `display=100`까지 한 번에 받을 수 있다(실측 확인) — 비공식
  엔드포인트는 `countPerPage=7` 고정이라 210개 글에 30번 호출이 필요했는데,
  공식 API는 3번이면 끝난다.

### 구현

`naver_blog_search(keyword, max_pages)`의 시그니처·반환 형태·목표 글 수
(`max_pages * 7` = 35/105/210개, PAGE_TIERS와 맞춤)는 그대로 유지하고 내부
구현만 바꿨다. `display=100`씩 `start`를 옮겨가며 호출하고, 응답이 요청한
`display`보다 적게 오면 더 이상 결과가 없는 것으로 보고 멈춘다. 비공식
엔드포인트 전용이던 `_strip_highlight`, JSON 하이재킹 접두사 처리, 관련
`config.py`/`settings.yaml`의 `naver.api_url`/`naver.headers` 설정을 모두
제거했다(전환 후 완전히 죽은 코드).

### 효과 (실측)

- **블로그 수집 자체가 훨씬 빨라짐**: 210개 글 기준 6.4~12.6초 → **0.66초**
  (호출 30번 → 3번).
- 정확도 유지: "신논현 카공" ground truth 재확인 — 공식 API가 돌려주는 글
  풀(ranking)이 비공식 엔드포인트와 달라서 ground truth 절대값 자체는 다르게
  나왔지만(40개→26개, 애초에 다른 70개 글 집합이라 자연스러운 차이), recall
  비율은 25/26(96%)로 여전히 높은 수준 유지.
  - "강남 맛집" 전체 파이프라인: mode=results, 확신 후보 30개, **32.5초**만에
    완료(카카오 검증 병렬화 효과까지 더해져 이전 대비 훨씬 빠름).
  - "부산여행": mode=overview, 지역 8곳(해운대/광안리/남포동/기장/서면/부산역/
    영도/전포) — 12장에서 설계한 흩어짐 판단도 새 데이터 소스에서 그대로 잘
    작동함을 확인.

### 후속 정리: "7개 단위"는 비공식 API의 흔적일 뿐이었다

전환 직후엔 호환성을 위해 `naver_blog_search(keyword, max_pages)`가 내부적으로
`max_pages * 7`을 목표 글 수로 계산하도록 남겨뒀다(비공식 엔드포인트의
`countPerPage=7` 흔적). 공식 API 파라미터 문서(`display` 최대 100, `start` 최대
1000)를 다시 보고, 이 "7 단위" 제약이 더 이상 필요 없다고 판단해 정리했다.

- `naver_blog_search`의 매개변수를 `max_pages`(페이지 수) → `target_count`(글 수
  그대로)로 바꾸고, `×7` 계산을 제거했다.
- `service.py`의 `PAGE_TIERS = [5, 15, 30]`(→ 35/105/210개)를
  `COLLECTION_TIERS = [100, 200, 300]`으로 바꿨다 — 공식 API의 `display` 상한
  (100)에 맞춰 각 tier가 정확히 1/2/3번 호출로 끝난다.
  `config.py`/`settings.yaml`의 `search.max_pages`도 `search.target_count`로
  이름을 맞췄다.
- 재검증(강남 맛집/부산여행/성수동 브런치): mode 판단(results/overview) 그대로
  유지, 후보 개수·소요 시간(34~47초)도 기존과 비슷한 수준 — 이번 정리는 이름과
  tier 크기만 바뀐 것이고 판단 로직(확신 후보 개수, 흩어짐 비율 등)은 그대로라
  동작이 크게 달라지지 않았다.

## 14. 설정 디렉토리 이름 정리와 죽은 설정 필드 제거

`backend/config/`(YAML 설정 파일 디렉토리)와
`backend/blog_place_collector/config.py`(설정 로딩 모듈)의 이름이 겹쳐 헷갈린다는
지적을 받아 정리했다.

- **디렉토리 이름 변경**: `backend/config/` → `backend/settings/`. 내용물이
  "사용자가 조정하는 설정값"이라 이름을 그에 맞췄고, `config.py`와의 충돌을
  없앴다. 함께 바꾼 곳: `config.py`의 `SETTINGS_PATH`/`EXAMPLE_SETTINGS_PATH`,
  `docker-compose.yml`의 volume 마운트 경로, `README.md`/`README_KO.md`의 복사
  명령, `setup-nginx-https.sh`의 안내 문구. `.gitignore`는 경로 prefix 없는
  bare `settings.yaml`이라 그대로 `backend/settings/settings.yaml`을 덮어서 수정
  불필요(`git check-ignore`로 확인). Dockerfile은 `COPY . .`라 경로 영향 없음.

- **죽은 필드 제거**:
  - `search.top_n`(`TOP_N`) — 대입만 되고 참조가 전혀 없어 완전 삭제.
  - `search.keyword`(`KEYWORD`/`AREA_KEYWORD`) — `naver.py`/`kakao.py`의 함수
    기본값으로만 쓰였는데 `service.py`가 항상 keyword/area_keyword를 명시적으로
    넘겨서 기본값이 실제로 쓰인 적이 없다. 필드를 삭제하고 함수 인자를 정리했다:
    `naver_blog_search(keyword, ...)`는 keyword 필수, `get_area_anchor(area_keyword)`는
    필수, `search_place`/`_search_documents`의 `area_keyword`는 기본값을 `None`으로
    바꿨다(nationwide=True 경로는 area_keyword를 안 쓰므로 안전 — 실측 확인).
  - `kakao.local_search_url` — 카카오 API 고정 엔드포인트라 사용자가 바꿀 이유가
    없다. YAML에서 빼고 `NAVER_*_SEARCH_URL`처럼 `config.py`에 상수로 하드코딩.
    YAML의 `kakao:` 섹션 통째로 삭제.
  - 유지한 필드: `search.target_count`, `search.kakao_search_radius`.

- **배포 주의(과거 KeyError 사고 재발 방지)**: `settings.yaml`은 gitignore라
  배포 서버 파일은 git push로 갱신되지 않는다. 이번에 (1) YAML 키 2개(`top_n`,
  `keyword`)와 `kakao:` 섹션을 없앴고 (2) 파일 경로를 `backend/config/` →
  `backend/settings/`로 옮겼다. `settings.example.yaml`(git 추적)과 로컬
  `settings.yaml`은 새 스키마로 갱신했지만, **배포 서버에서는 사람이 수동으로
  `backend/config/`를 `backend/settings/`로 옮기고 YAML을 새 스키마(search만,
  target_count/kakao_search_radius 2키)로 맞춰야 한다.** 옛 파일에 `top_n`/
  `keyword`/`kakao`가 남아 있어도 `config.py`가 더는 그 키를 읽지 않아 KeyError는
  안 나지만(하위호환 OK), 파일 경로가 안 맞으면 config.py가 example로 fallback
  하므로 경로 이전이 필요하다.

- 검증: `pytest backend/tests` 6 passed. `main.py` 부팅 후 `/api/health`가
  `settings: true` 반환(새 경로 인식). 실 API로 `naver_blog_search`(성수동 카페),
  `get_area_anchor`(성수동), `search_place` local/nationwide 모두 정상 동작 확인.
  `docker build`도 통과(이미지 안에서 config 로드까지 확인).

## 15. settings YAML 제거와 .env 루트 이동

- **결정**: `backend/settings/`(settings.yaml / settings.example.yaml)를 통째로
  없애고, 남은 두 값을 `config.py` 대문자 상수로 옮겼다:
  `TARGET_COUNT = 300`, `KAKAO_SEARCH_RADIUS = 5000`.
- **이유**: settings.yaml은 gitignore라 배포 서버 파일이 git push로 갱신되지
  않았고, 키 이름을 바꿀 때마다 서버가 KeyError로 죽거나(실제 사고) 사람이 수동으로
  맞춰야 했다(14절). 남은 값은 비밀이 아니고 사용자가 바꿀 일도 거의 없으므로 코드
  상수로 두는 게 맞다. 이제 설정 변경 = 코드 변경 = git 배포.
- 함께 정리: `PyYAML` 의존성 제거, docker-compose의 settings.yaml 볼륨 마운트 제거,
  `.gitignore`의 `settings.yaml` 줄 제거, `/api/health`의 `credentials.settings`
  필드 제거(프론트엔드는 쓰지 않음, test_api만 갱신).
- **.env 루트 이동**: `backend/.env` → 저장소 루트 `.env`(`.env.example`도 루트).
  `config.py`는 `PROJECT_ROOT.parent / ".env"`를 읽고 docker-compose `env_file`도
  `.env`. git으로 배포되지 않는 파일은 이제 루트 `.env` 하나뿐이다.
- **배포 서버 수동 작업**: `mv backend/.env .env` 후
  `docker compose up -d --build`. 남아 있는 `backend/settings/` 디렉토리는 더 이상
  읽지 않으므로 지워도 된다(`rm -rf backend/settings`).

## 16. 네이버 초당 10건 한도 대응

- **문제**: 네이버 Open API 한도는 클라이언트 ID 기준 초당 10건이고 blog/local
  검색이 한도를 공유한다(응답 헤더 `x-rate-limit: 10`, 1초 단위 리셋 — 실측).
  카카오 검증 실패 시 병렬로 부르는 `naver_local_search`와 tier별 블로그 수집이
  겹치면 429가 났다.
- **결정**:
  - 모든 네이버 호출을 `_naver_get` 한 경로로 모으고, 프로세스 전역·스레드 안전한
    최소 간격 rate limiter(`NAVER_REQUESTS_PER_SECOND = 8`, 버스트 없음)를 건다.
    10이 아니라 8인 건 서버 측 창 경계와 시계 오차 여유.
  - 429를 받으면 `Retry-After` → `x-rate-limit-reset` → 1초 순으로 대기 시간을
    정해(0.2~3초로 클램프) 최대 3회 재시도하고, 그 동안 limiter 전체를 뒤로 미룬다.
  - **tier 증분 수집**: sim 정렬은 앞쪽 결과가 고정이라(실측) tier가 올라갈 때
    처음부터 다시 받지 않고 `start=len(posts)+1`로 모자란 만큼만 이어 받는다.
    결과가 요청보다 적게 오면 소진으로 보고 더 요청하지 않는다.
  - **tier 간 검증 캐시**: `_verified_candidates`에 이름→검증 결과 캐시를 넘겨,
    이전 tier에서 검증한 이름은 다시 조회하지 않는다(같은 이름이면 결과도 같다).
- 테스트: `backend/tests/test_naver_client.py`(limiter 간격, 429 재시도, 증분 수집).
